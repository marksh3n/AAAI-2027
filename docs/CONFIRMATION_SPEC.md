## 2. Engine, sampling and data saved (task 4)

Sources and rollouts are generated by the same engine with the same settings. Both go through
`src/recovery/run_rollouts.py`; a source trace is a continuation of the empty prefix.

| Setting | Value |
|---|---|
| Model / tokenizer | `deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B` @ `ad9f0ae0864d7fbcd1cd905e3c6c5b069cc8b562` (both) |
| Engine | vLLM 0.10.2, transformers 4.56.2 (the Modal image the ceiling rollouts ran on) |
| dtype | float16 (generation and extraction; the dev activations were fp16) |
| Sampling | temperature 0.7, top_p 0.95, no top_k, per-request seed `prefix_seed(0, prefix_id, round)` |
| BOS | **one**: the chat template's own. Prompt ids are `tokenizer(prompt, add_special_tokens=False)` and are given to vLLM as token ids, never as a string. The runner asserts exactly one leading BOS and that vLLM echoes the ids unchanged. |
| Budget | 32768 tokens per trace. A rollout from cut c gets `max_tokens = 32768 − c` (bundle.py refuses anything else). |
| Saved | Sources: prompt ids, every generated token id, n_gen, finish reason, seed, text, answer, grade. Bank: per continuation the sha256 of its token ids, n_gen, finish reason, seed, text, answer, grade. Per prefix: cut position, prefix ids and their sha, max_tokens. Run configs (model, revision, vLLM version, temperature, top_p, cap) and every file's sha256 are recorded in the bundle. |

Hidden states for the monitors are computed by an HF transformers forward pass in fp16 at the same
revision. The input is the exact prompt ids plus generated ids, and the state is read at token
index c − 1, layer 20 = `hidden_states[21]`. They are not recomputed from retokenized text.

Cut points: `CHECKPOINTS = (2048, 4096, 6144)`. A source trace gets rollouts at a checkpoint only
when it is **live** there (§4), with `K_PREFIX = 8` continuations. Each problem also gets
`K_T0 = 8` fresh samples from the prompt (the t0 bank), drawn as round 1 of the same prompt
records, so their seeds differ from the sources' round 0.

All are fit on **all** development data by `fit_monitors.py`. Thresholds are chosen on

| Name | Model | Features | Checkpoints | Role |
|---|---|---|---|---|

The model and feature definitions are probe_cmp's `models.py`, step for step.
`tests/test_confirm.py` checks that `src/confirm/monitors.py` gives the same out-of-fold
predictions and the same C as probe_cmp for all four, so the frozen tree is the probe_cmp tree.

- **Training rows at c**: untruncated traces that reach c, in problems with a correct and a wrong
  such trace (probe_cmp's population at c alone). At 6144 this is the 342-trace / 74-problem
  cohort. Truncated traces are left out of training, as in dev. In confirmation they are live
  until the cap, are scored, and count as wrong.
- **Operating point**: flag a trace when its score is strictly above τ_c. τ_c is the (1 − 0.25)
  quantile of dev scores over **live** traces at c in **all** problems (Q_DEV = 0.25, fixed before
  any policy result). A training trace enters with its out-of-fold score (5 grouped folds, seed 0).
  Every other live trace is scored by the final model, which never saw it.
- **Saved**: `<name>@<c>.joblib`, plus `manifest.json` with C, τ_c, dev out-of-fold AUROC with CI,
  the training trace-id hash, the sha256 of every input file and of the `src/confirm` code, and
  library versions. Scoring refuses any monitor whose file hash does not match the manifest.

## 4. Definitions

- **Attempt**: one source trace. It is one run of a policy on its problem.
- **Live at c**: the trace is still generating after c tokens (n_gen > c, so no EOS among the first
  c), and its first c tokens contain no `</think>`. Policies act only on live traces. Every other
  attempt keeps its own outcome and cost.
- **Pre-answer at c** (story 2, S7): primary rule "stated", `bundle_lib.cut_rules`. The cut is live,
  the decoded prefix has no `\boxed`, and it does not state the trace's own final answer.
  - "States" means the value follows a cue on the same line, within 40 characters. The cues are
    `final answer`, `answer is`, `answer:`, matched case-insensitively.
  - In regex form: `(?i:final answer|answer is|answer:)[^\n]{0,40}?(?<![\w.])VALUE(?!\w|\.\d)`.
    VALUE is the normalized final answer (`ceiling.norm`). The prefix is normalized the same way:
    `\left` / `\right` removed, `\dfrac` and `\tfrac` turned into `\frac`.
  - Two sensitivity rules are pre-registered, reported beside the primary and not tested:
    - **strict**: no `\boxed`, and the final answer value appears nowhere as a standalone number
      (`ceiling.answer_flags`);
    - **think_boxed**: no `\boxed` only (`</think>` is already excluded by live).
- **Available population at c**: every live trace at c. **Matched cohort**: traces live at every
  checkpoint, used only for timing comparisons. Both are reported, along with counts per
  checkpoint.
- **Outcome**: 1 when the final answer is correct under math_verify, 0 otherwise. Truncated
  traces count as 0.

## 5. Arms and their cost (task 2)

Cost is **total generated tokens per attempt**. That includes tokens later discarded, every
replacement, every extra vote, and any rollouts used to decide (selection cost). Hidden-state
monitors add no generated tokens: the state exists from generating the prefix, and the readout
is one dot product or a 150-tree ensemble.

For a live attempt i flagged at checkpoint c (with outcome y_i and n_i tokens if kept):

| Arm | Outcome if flagged | Tokens if flagged |
|---|---|---|
| no intervention | y_i | n_i |
| restart (fresh sample from the prompt) | r0, the problem's t0 bank mean | c + L0 |
| backtrack (fresh continuation of the trace's own prefix at c′ = 2048 for c = 4096, 4096 for c = 6144) | r(c′), that prefix's bank mean | c + L(c′): c′ kept, c − c′ discarded, then the new tail |
| aggregation, m extra samples + plurality vote (not flagged: funded per attempt) | A_m: exact over every m-subset of the problem's t0 bank, plus the attempt's own answer; ties split evenly | n_i + m·L0 |

- A replacement's outcome and length are bank means: the expected value of one fresh draw. This
  is unbiased because the decision uses the source prefix only, and the bank is sampled
  independently by the same engine. That last assumption is checked (§8).
- Policy arms per checkpoint and action:
  - **fixed**: every live trace;
  - **random**: each live trace with probability π;
  - **monitor-triggered**: every live trace with score above τ_c.
- Aggregation is m = 2 (maj@3) for the tests; m = 4 is reported.
- The **rollout-ranked** arm (cross-fitted r̂ halves, q = 0.25) is a diagnostic for story 1, not a
  policy under test. Its tokens include the 4 selection rollouts per live trace.
- The old dev oracle plots excluded that cost and compared equal shares flagged. They are offline
  estimates, not equal-compute evidence.

## 6. Matching on total tokens

A monitor-triggered policy P spends `S_P = Σ_i (tok_i(P) − n_i)` extra tokens over no
intervention. A comparator whose spend is linear in its rate (random, aggregation) gets the rate
`π = S_P / S_C(1)`, where `S_C(1)` is its extra spend at π = 1. Its accuracy is
`mean(y) + π·Σ gain_i / N`, and its expected total tokens equal P's exactly.

- The match is redone inside every bootstrap draw, so the CI includes matching uncertainty.
- π > 1: the comparator is capped at 1 and flagged "cannot spend that much".
- π < 0, or P saves tokens while the comparator can only add them: no rate matches. The
  comparator falls back to no intervention, which spends at least as much, and is flagged.
- Each row reports the share of draws where the match failed.
- Equal fractions flagged are never used for a comparison.
- For S6 (primary monitor vs `len`), both policies are compared through their value over the
  token-matched random line: `V(P) = acc(P) − acc_random(T_P)`.

## 7. Endpoint, tests, uncertainty (task 3)

- **Endpoint [JADEN: confirm]**: accuracy per attempt at equal total generated tokens, over **all
  attempts of all problems**. Restricting to mixed problems would condition on outcomes.
  Within-problem AUROC stays on the mixed problems among the rows scored, since other problems
  have no pairs.
- **Uncertainty**: problem-cluster bootstrap, B = 2000, seed 0. Draws are shared by every arm at a
  checkpoint, so all deltas are paired. 95% percentile CIs.
- **Primary H1**: at c = 4096, `lr_raw_L20`-triggered restart at its frozen τ beats **both**
  (a) token-matched random restart and (b) token-matched maj@3 aggregation.
  - It holds only if both lower 95% bounds exceed the margin **[JADEN: `margin_pp`]**
    (an intersection-union test, so no multiplicity adjustment).
  - The script prints no verdict while the margin slot is empty.
- **Secondary**, Holm at α = 0.05 over S1–S7; p-values are Wald, from the bootstrap SE:

  | ID | Checkpoint | What | Compared with |
  |---|---|---|---|
  | S1 | 4096 | primary-triggered backtrack | random backtrack |
  | S2 | 2048 | primary-triggered restart | random restart |
  | S3 | 6144 | primary-triggered restart | random restart |
  | S4 | 6144 | tree-triggered restart | random restart |
  | S5 | 6144 | tree-triggered backtrack | random backtrack |
  | S6 | 4096 | primary monitor's value over random | `len`'s value over random (is hidden-state value beyond observable length?) |
  | S7 | 6144 | tree AUROC on **live pre-answer** cuts, primary "stated" rule; strict and think_boxed reported beside it | `len` (story 2: the signal arrives before the answer) |

  - **S7 estimate-only branch** (`spec.S7_MIN_MIXED` = 500, pre-registered 2026-10-27). Count the
    mixed problems among live "stated" pre-answer cuts at 6144 in the confirmation data. This is a
    label count and reads no scores. If the count is below 500, S7 is reported as effect and 95% CI
    only, makes no claim, and leaves the Holm family, which is then S1–S6. Otherwise S7 is tested as
    above. The analysis applies this automatically and prints the count.
  - Why 500: on dev, 61 mixed problems give a CI half-width of about ±0.13 (scaled from the strict
    rule's ±0.19 at 30 problems; an estimate, not computed). 80% power for the dev-sized +0.065 needs
    an SE near 0.023, about 9× the clusters.
  - **[JADEN: `expected_mixed_6144_stated`]**: his projected count for this comparison, for
    planning only. The branch is decided on the observed count.

- **Descriptive, not tested**:
  - every AUROC (live, pre-answer, matched cohort) per checkpoint;
  - r̂ vs each monitor (story 1);
  - fixed arms, the rollout-ranked diagnostic, m = 4, and baseline-triggered policies.
- **Population [JADEN]**: problem list file and its sha256 (`gpu_prep.py t0` refuses any other),
  number of problems, samples per problem. **Sample size [JADEN]**.
- **Planning note for Jaden (dev, not a decision).** The dev dry run (2026-10-25) uses this
  design's metric, out-of-fold scores, the 87 ceiling problems and 522 attempts. Live cuts without
  a bank cannot be flagged.

  | Primary contrast | Δ | 95% CI |
  |---|---|---|
  | vs token-matched random restart | +1.1 pp | [−0.6, +3.1] |
  | vs token-matched maj@3 | +1.6 pp | [−0.1, +3.4] |

  - The primary monitor flagged 16% of live traces, spending about +400 tokens per attempt over
    no intervention (11,964).
  - At this size the half-width is about 1.8 pp. Detecting about 1 pp needs a few times more
    problems.
  - Both contrasts carry the dev source-vs-rollout gap (§8).

## 8. Validity checks and the source-vs-rollout gap

- **Resample check, per checkpoint**: replace every live trace (and separately the primary
  monitor's flags) with a fresh continuation of its own prefix. With one engine this must be ≈0.
- On dev it was not: source accuracy 0.527 vs mean prefix r̂ 0.600 at 512 in the ceiling cohort,
  shrinking to 5.1 and 3.0 pp at 2048 and 4096.
- The dev dry run's built-in check flags the same gap: +4.4 pp [+1.3, +7.6] at 2048 and +2.6
  [−0.3, +5.5] at 4096, so the check catches what it is meant to.
- If the check's CI at the decision checkpoint excludes 0:
  - the primary is reported with a flag;
  - the pre-specified sensitivity analysis (`analyze.py --keep rollout`) values kept live traces
    at their prefix's bank mean;
  - both are reported.

The dev gap is **unexplained**. These causes were ruled out on dev:
- mixed selection (−0.039 residual after it);
- length selection (still −2.3 pp at 512 when length-matched);
- BOS (same gap in the one-BOS pilot block and the two-BOS main block);
- grading (448/448 source labels reproduce);
- temperature (0.7 confirmed).

Candidates still open:
- (a) the main block's engine version and settings were never recorded;
- (b) dev rollouts were fed the **retokenized text**, not the sampled token ids. A non-canonical
  tokenization changes the prefix the model conditions on, even when the length matches, and
  only length drift was checked;
- (c) anything else that differed between the 2026-09 generation runs and the Modal rollouts.

The frozen design removes each of these by construction: one engine for sources and bank, exact
token ids with no retokenization, one BOS, 32768 − c budgets. So the gap should not carry over,
and the resample check tests that directly. It remains attached to every dev number that mixes
source outcomes with rollouts: the oracle plots and dev r̂ calibration.

## 9. Wording rules (task 5)

- r̂ is "rollout-estimated" (K = 8; 4 per half in cross-fitting). It is not a perfect monitor and
  not a ceiling on what a monitor could do.
- The rollout-ranked plots are offline estimates. Their selector's rollouts are not in the plotted
  cost, and equal shares flagged are not equal tokens.
- No "no extra token cost": token changes are reported with CIs. The rerun with token CIs (oracle_v4,
  all problems) has the following, before the ~35–47k selection tokens per trace the ranking needs:

  | Arm | Token change per trace | 95% CI |
  |---|---|---|
  | backtrack at 2048 | −24 | [−233, +163] |
  | restart at 512 | −38 | [−279, +199] |
- No "audit but not correct". On development cohorts, the tested probes have not shown useful
  intervention value. That does not show hidden states lack the information.
